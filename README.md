# TransitAssist: map-first transit prototype (simulated data)

Born from a real problem: standing at a bus stop with no idea when the bus will come or how crowded it is.
This prototype shows a Leaflet/OpenStreetMap map with stops, routes and **simulated** moving buses, and lets a
commuter submit a "please stop for me" request that is saved to MySQL.

## What is real and what is simulated
| Real | Simulated (generated by the app) |
|---|---|
| Map tiles (OpenStreetMap), routes/stops/stop requests stored in MySQL, REST API, validation | Bus positions, ETAs, crowding level, the buses themselves |

A stop request means **a row was saved in the database**. No driver app exists, so nothing is delivered.
Status stays `PENDING`; `ACKNOWLEDGED` is reserved for a future driver app and nothing sets it.
Stop coordinates are approximate and the routes are fictional, not real Bhopal transit data.

## Architecture
```
Browser (index.html + app.js + Leaflet)
   |  fetch() JSON, buses polled every 2 s
   v
Controller  (HTTP + @Valid)   RouteController, StopController, BusController, StopRequestController
   v
Service     (business rules)  RouteService, StopService, BusSimulator (+RoutePath maths), StopRequestService
   v
Repository  (Spring Data JPA) RouteRepository, StopRepository, RouteStopRepository, StopRequestRepository
   v
MySQL  routes | stops | route_stops | stop_requests
```
Errors from any layer go to `GlobalExceptionHandler` and come back as one JSON shape.

## Database
```
routes 1 ---< route_stops >--- 1 stops        (many-to-many, route_stops.stop_order = position on route)
routes 1 ---< stop_requests >--- 1 stops      (stop_requests.bus_code = "101-A", status, created_at)
```
Buses are **not** tables: they are computed from the clock (see `RoutePath`), so `stop_requests` stores the bus code as text.
Sample data is inserted by `DataSeeder` only when the tables are empty. Restarts never duplicate or overwrite.

## Run on Windows 11 / IntelliJ
1. **Create the new database once** (a new, empty DB; your old `transitassist` database is not touched). In MySQL as root:
   `mysql -u root -p < database\00_create_database.sql`
2. Open the folder in IntelliJ (Project SDK: Java 21).
3. Run > Edit Configurations > TransitassistApplication > Environment variables:
   `DB_USERNAME=transitapp;DB_PASSWORD=<your password>`  (never put the password in a file)
   To use a different database name add `DB_NAME=<name>`.
4. Run `TransitassistApplication`, open http://localhost:8080/
5. Tests need **no MySQL and no password** (in-memory H2): `.\mvnw.cmd test`

If `transitapp` has a different host or the GRANT fails, adjust the user in `00_create_database.sql`.

## API
Errors: `{"timestamp":"...","status":400,"error":"Bad Request","message":"Validation failed","path":"/api/stop-requests","fieldErrors":{"stopId":"stopId is required"}}`

| Method | Path | Success | Errors |
|---|---|---|---|
| GET | `/api/routes` | 200, routes with ordered `stops` | |
| GET | `/api/routes/{id}` | 200 | 404 |
| GET | `/api/stops` | 200 | |
| GET | `/api/stops/nearby?lat=&lng=&radius=1000` | 200, nearest first, max 20, radius 1..5000 m | 400 bad/missing params |
| GET | `/api/buses` | 200, simulated buses | |
| POST | `/api/stop-requests` | 201 + Location, status `PENDING` | 400 invalid/unknown bus/stop not upcoming, 409 duplicate within 10 min |
| GET | `/api/stop-requests/{id}` | 200 | 404 |
| GET | `/api/stop-requests` | 200, latest 10 | |

```
curl.exe "http://localhost:8080/api/stops/nearby?lat=23.229&lng=77.42&radius=500"
curl.exe -X POST http://localhost:8080/api/stop-requests -H "Content-Type: application/json" -d "{\"busCode\":\"101-A\",\"stopId\":2}"
```
(Use a `stopId` and `busCode` that currently appear in `/api/buses` `upcomingStops`; a bus cannot be asked to stop at a stop it already passed.)

## Limitations (say these honestly)
- Buses move in straight lines between stops, back and forth at a constant ~21.6 km/h; no roads, traffic or dwell time.
- ETAs and crowding are formulas, not predictions. Nothing is learned from real data.
- Polling every 2 s re-reads route data from MySQL each time; a real system would cache and use push updates.
- Nearby search computes distance in Java over all stops; at scale you would filter in SQL with an index.
- No authentication, so anyone can post requests. `ddl-auto=update` is for development; production would use Flyway.
- Pending requests never expire.
